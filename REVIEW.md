# Code Review of Starter Application (`app/main.py`)

Below is the structured review of defects identified in the starter code, detailing the root cause, observable failing symptoms or test cases, and the applied architectural fixes.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–37) | Failed to compute shift start datetime using the record's attendance date; used naive division `int((punch_in - start).total_seconds() / 60)` which miscalculates negative differences; violated strict 10-minute grace period boundary rule (R2) where late is strictly `> 10:00`. | Punching in at exactly 09:40:00 for a 09:30 shift returned 10 late minutes instead of 0; overnight shifts crossing midnight resulted in negative or corrupted late minutes. | Constructed timezone-aware `shift_start_dt` combined with `att_date`, evaluated strict `diff_sec > 600`, and calculated late minutes from shift start using `int(diff_sec // 60)`. |
| 2 | `compute_work_hours` (lines 40–41) | Relied on Python's native `round()`, which performs banker's rounding (round-half-to-even) and suffers from floating-point precision inaccuracies, directly violating R4 (strict arithmetic half-up rounding). | Inputs producing intermediate work hours such as `9.115` rounded down to `9.11` instead of `9.12`. | Replaced with `decimal.Decimal` quantized with `ROUND_HALF_UP` to two decimal places on `diff_sec / 3600`. |
| 3 | `compute_overtime` (lines 44–47) | Did not enforce the mandatory 30-minute minimum threshold (R3); failed to advance `shift_end` by one calendar day for overnight shifts where `shift_end <= shift_start`. | Punching out 10 minutes past shift end awarded 10 minutes of overtime instead of 0; overnight shifts punching out on day T+1 threw negative overtime or inflated hours. | Advanced `shift_end` calendar day by 1 for overnight shifts (`shift_end <= shift_start`), and returned floored minutes only when `minutes >= 30`, returning 0 otherwise. |
| 4 | `create_employee` (lines 78–85) | Application-level existence check (`if db.employees.find_one(...)`) introduced a race condition under concurrent requests; accepted equal `shift_start` and `shift_end` without returning 422. | Concurrent duplicate employee creation requests both succeeded with 201; creating an employee with shift 09:30 to 09:30 succeeded. | Initialized a unique index on `emp_code` at startup, handled `pymongo.errors.DuplicateKeyError` returning 409, and validated `shift_start != shift_end` with 422. |
| 5 | `list_employees` (lines 89–96) | Off-by-one pagination bug where `skip = page * page_size` skipped the first page when `page=1` (`skip=20` instead of `0`); `total` called `count_documents({})` ignoring active department filters; lacked sorting by `emp_code` ascending. | Requesting `page=1` returned items starting from index 20; filtering by department showed the total collection count; employee list order was nondeterministic. | Corrected skip offset to `(page - 1) * page_size`, filtered `count_documents(q)`, and added cursor-level sort `[("emp_code", ASCENDING)]`. |
| 6 | `punch_in` (lines 100–121) | Vulnerable check-then-act concurrency race condition allowed simultaneous punch-ins on the same day for an employee; did not check employee existence (404); computed attendance date from system clock instead of IST (R1). | Two simultaneous punch-in requests yielded two 201 responses; punch-in for unknown employee succeeded; early morning punches in overnight shifts were attributed to the wrong date. | Created a unique composite index on `(emp_code, date)` and caught `DuplicateKeyError` to return 409; verified employee existence with 404; implemented `get_attendance_date` with IST timezone and overnight boundary handling. |
| 7 | `list_attendance` (lines 125–150) | In-memory sorting and pagination `docs = list(db.attendance_logs.find(q))` loaded all documents into server RAM, failing scalability requirements on 100k documents; accepted inverted date ranges (`date_from > date_to`) with 200. | Server memory exhaustion and latency timeouts on large datasets; passing `date_from=2026-07-10&date_to=2026-07-01` returned empty items with 200 instead of 422. | Replaced with indexed database cursor sorting `[("date", DESCENDING), ("emp_code", ASCENDING)]` with `.skip()` and `.limit()`; validated `date_from <= date_to` returning 422. |
| 8 | Database Initialization & Explain Plan (Startup) | No database indexes were defined or initialized at startup, resulting in full collection scans (`COLLSCAN`) across all endpoints and failing explain plan verification. | Running `GET /admin/explain/{endpoint}` showed `stage: COLLSCAN` across all queries and aggregation pipelines. | Configured FastAPI `lifespan` handler to idempotently create compound and unique indexes on startup for `employees` and `attendance_logs`. |
| 9 | DateTime Serialization & MongoDB `_id` Leakage | Returned MongoDB internal BSON `_id` in API payloads and serialized timestamps as strings or BSON objects instead of epoch milliseconds per OpenAPI schema. | Response payloads violated OpenAPI specification with fields like `"_id": "64f..."` and ISO timestamp strings instead of integer epoch milliseconds. | Implemented response serializers (`serialize_employee`, `serialize_attendance_log`, `serialize_history_entry`) that omit `_id` and normalize UTC datetimes to epoch milliseconds. |
| 10 | MongoDB Client Naive DateTime Handling | `MongoClient` initialized without `tz_aware=True`, causing PyMongo to return offset-naive datetimes that raised runtime `TypeError` when compared against timezone-aware datetimes. | Punch-out validation comparing `punch_out_dt <= punch_in_dt` crashed with `TypeError: can't compare offset-naive and offset-aware datetimes`. | Configured `MongoClient(..., tz_aware=True)` and normalized all incoming timestamps to UTC datetimes. |
| 11 | Missing Endpoints & Analytics Pipelines | Endpoints for `/attendance/punch-out`, `/attendance/{emp_code}/{date}`, and all analytics aggregations were either missing or placeholders. | Core business functionality and analytics queries returned 404/405. | Implemented robust endpoints backed by MongoDB aggregation pipelines (`$setWindowFields`, `$densify`, `$lookup`, `$rank`, CAS atomic updates). |
| 12 | Explain Endpoint Response Schema Mismatch | Explain endpoint returned the raw MongoDB command dictionary directly rather than the required response envelope schema `{ "endpoint": ..., "collection": ..., "explain": ... }`. | Automated OpenAPI contract validation failed on `GET /admin/explain/{endpoint}` due to missing `endpoint` and `collection` keys. | Wrapped explain output in the compliant schema `{ "endpoint": endpoint, "collection": collection, "explain": plan }`. |

---

### Examined and Decided Not a Defect

1. **Calendar Dates Stored as ISO Strings (`"YYYY-MM-DD"`):**
   - *Investigation:* Evaluated converting `date` and `joined_on` to BSON datetimes.
   - *Conclusion:* Storing calendar dates as string representations (`YYYY-MM-DD`) accurately captures timezone-agnostic calendar days without risking implicit UTC midnight shifts across different timezones. This perfectly matches `DATA_MODEL.md`.

2. **Absence of `history` or `half_day` in Legacy Records:**
   - *Investigation:* Sample and seeded documents occasionally omit the `history` array or `half_day` boolean.
   - *Conclusion:* Handled via application-level defaulting (`history: []` and `half_day: False`) during serialization and CAS matching conditions (`$or` covering missing fields), preserving backwards compatibility without requiring schema mutations.
